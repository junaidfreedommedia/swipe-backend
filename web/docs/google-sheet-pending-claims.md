# Monthly pending claims

The monthly tab uses one set of yellow headings at row 1. Detailed previous-month pending rows come immediately underneath, followed by the current month's original claim rows. In pending rows, A shows the original order date, B shows the claim/order number, C shows its status and D shows the complete original claim date (for example 8/26/2026) in full date format. Both B (Order Number) and D (Claim Date) use background #E8F0FE and text #1A73E8. E:J show merchant, customer email, refund/reorder status, processed amount, notes and closing date from the original claim mapping. The original order date is retained in the A-cell note and the full claim date in the D-cell note. Order date and order number align with the same main headings as the original claim rows. The blue colors in B and D apply only to the previous-month pending block. Pending cells use the same black borders and alternating white/light-gray row shading as the main table. Only the hidden refund/reorder totals in Z/AA stay blank. The heading row stays frozen. The former separate title, count and duplicate headings are removed; the pending count is available in the A1 note.

Only sheet-enabled claims belonging to the same merchant, filed before the tab month and still REVIEWING, IN_REVIEW or APPROVED, are listed. Month selection uses GOOGLE_SHEET_TIMEZONE (default Asia/Karachi). Completed or no-longer-eligible claims disappear from the pending block, while their full original rows remain in their creation-month tabs. Missing database records stop refresh rather than silently removing an unverified claim.

Original rows retain bare internal IDs in Y. Pending rows use pending:<claim ID> in Y, which prevents them being treated as empty templates or real original claim rows. AN1 contains the layout marker. K:AN remain hidden. Automatic status backfills ignore the prefixed IDs. The main writer preserves the blue pending Order Number and Claim Date style and skips placeholder insertion in pending rows.

Google's native DATE table type forces a uniform display pattern. While pending rows exist, A and D use COLUMN_TYPE_UNSPECIFIED. Pending A uses a numeric order date with DATE format M/d/yyyy (or stays blank when the order date is unavailable), D uses the numeric original claim date with DATE format M/d/yyyy, and H has explicit CURRENCY format $#,##0.00. Original A/D use numeric dates with M/d/yyyy. Normal claim writes, missing-row restoration and monthly migration convert original order and claim dates to date serials when needed, preserving date semantics. With no pending rows, both columns return to DATE types. Both pending refresh and normal table finishing maintain these formats; live checks assert formatted display values as well as raw values.

Normal claim sync writes the original row and then refreshes the merchant's pending blocks. Only the current month receives new carryovers. GoogleSheetPendingClaims runs every 15 minutes, creates the current monthly tab even without a new claim, and catches up after downtime. The backend and Google connection must be running. Disabled merchant sheets are skipped; failed scheduled refreshes retry on the next run.

Opening or refreshing Store Detail reads the store without starting or waiting for Google Sheet repair. Sheet setup remains on the sheet-enable action; claim changes and the scheduled pending job continue updating sheets independently of page visits. Store access checks, billing checks, claim counts and sheet links are unchanged.

Both older layouts are recognized: the AC:AN side table and the three-column list above the main header. Migration removes only the managed list area and places the real main table header at row 1. Subsequent updates resize only the leading pending block. Row movement, values, formats and marker writes form one atomic batch under the shared per-tab queue and Mongo lease. Retries reread the actual layout. Empty/template-only gaps before the last pending ID are recovered from eligible database claims without moving original rows. Unknown content or original claims inside that span still stop the update.

Existing-claim saves on an established canonical table update only that claim's original row; they do not rebuild the table or run layout migration. Mixed-layout repair retains each original's existing position and ignores pending IDs. New originals and missing-original recovery cannot reuse gaps inside the pending block. Duplicate repairs log their affected ranges, and pending recovery logs its repaired gap count. Regression tests cover reorder followed by refund, every intermediate write, pending-gap recovery, original-row positions, and refusal to overwrite manual content.

Summary formulas sum Z and AA. Pending rows can display a processed amount in H, but Z/AA remain blank, so totals include only original claim rows. Before and after each pending update, all evaluated original A:AA values (including totals) are compared after excluding the managed pending rows. IDs are also read back to detect missing or duplicate copies. Main date values, complete pending details, borders, shading and complete date displays are verified in live migration/update tests, including pending claims with a nonzero processed amount.

The shared Sheets connection paces requests to one every 1.2 seconds and retries explicit HTTP 429 responses with bounded backoff. Ambiguous failed mutations are not automatically replayed. Tests cover both legacy migrations, growing/shrinking/empty pending blocks, original claim updates and appends, numeric original dates, placeholder protection, concurrency, month rollover, merchant isolation and unchanged totals.
